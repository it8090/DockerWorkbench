# 构建、发行与自动更新

公开仓库：[it8090/DockerWorkbench](https://github.com/it8090/DockerWorkbench)。仓库根目录包含 `code/`、`docs/`、README、MIT LICENSE 和 `.github/`。

## 自动发布

1. 更新并核对四处版本：`code/package.json`、`code/src-tauri/Cargo.toml`、`code/src-tauri/tauri.conf.json`、`code/core/internal/workbench/dispatch.go`；同步 Cargo.lock 中本包版本。
2. 更新 CHANGELOG，新增 `docs/releases/版本号.md`。
3. 运行相关检查，使用中文提交说明，推送 `main`。
4. 创建并推送对应标签，例如：

```sh
git tag -a v0.1.4 -m "发布 0.1.4，增加自动更新"
git push origin v0.1.4
```

`.github/workflows/release.yml` 在版本标签推送时运行，也可从 Actions 手动选择已有版本标签重试。四个平台分别测试、打包并签署更新包：

| 平台 | Rust target | 安装包 / 更新包 |
| --- | --- | --- |
| macOS Apple Silicon | aarch64-apple-darwin | dmg / app.tar.gz |
| macOS Intel | x86_64-apple-darwin | dmg / app.tar.gz |
| Windows x64 | x86_64-pc-windows-msvc | NSIS exe |
| Linux x64 | x86_64-unknown-linux-gnu | deb / AppImage |

只有四个平台全部成功，汇总任务才会执行。汇总检查平台齐全，用 Minisign 验证每个更新包签名，再生成 `latest.json` 和 `SHA256SUMS.txt`。产物先传入 Draft Release，全部上传后才公开并设为 latest。已公开的同名版本拒绝覆盖，后续修复应增加版本号。

CI 构建结果不替代对应系统的安装和功能验收。Apple Developer ID / 公证及 Windows Authenticode 签名需要独立的发行身份；Tauri 更新签名不能替代操作系统签名。

## 更新密钥

本仓库的更新公钥与 HTTPS 地址固定在 `code/src-tauri/tauri.conf.json`，前端不能修改。GitHub Actions 需要两个 Repository Secrets：

- `TAURI_SIGNING_PRIVATE_KEY`：私钥文件内容。
- `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`：私钥口令。

私钥和口令不进入仓库、构建产物或文档。应在可信位置备份；遗失密钥后，已安装应用无法信任新密钥签发的更新。公开仓库的 PR 检查不使用签名密钥。

独立分发本项目时，请生成自己的密钥，将应用 identifier、公钥和更新地址换成自己的发行源，不能沿用本仓库发行身份：

```sh
cd code
pnpm exec tauri signer generate -w ~/.tauri/docker-workbench.key
```

按 [Tauri updater 文档](https://v2.tauri.app/plugin/updater/) 设置本地构建所需环境变量；正式打包时不要将密钥写入 `.env` 或命令历史。

## 本地构建与验证

```sh
cd code
pnpm install --frozen-lockfile
pnpm build
pnpm test
pnpm core:test
cargo fmt --manifest-path src-tauri/Cargo.toml -- --check
```

仅验证本地打包、不产生签名更新包：

```sh
pnpm desktop:build --ci --config src-tauri/tauri.ci.conf.json
```

正式构建在设置签名环境变量后执行 `pnpm desktop:build --ci`。安装包位于 `code/src-tauri/target/release/bundle/`，指定 `--target` 时位于对应 target 子目录。

`code/scripts/stage-release.mjs` 给各平台文件添加版本与架构名称，避免合并时覆盖。`code/scripts/assemble-release.mjs` 在汇总目录验证签名并生成清单，需要系统已安装 Minisign。发布工作流自动安装此工具。

macOS 下载校验：

```sh
shasum -a 256 -c SHA256SUMS.txt
```

Linux 可用 `sha256sum -c SHA256SUMS.txt`，Windows 可用 `Get-FileHash 文件名 -Algorithm SHA256` 与清单逐项比较。

## 用户更新行为

0.1.4 起，正式构建启动后检查更新，也可在右下角“软件更新”中手动检查。检查失败不影响 Docker 连接。用户确认后下载并校验签名；安装失败必须重新检查，不能复用已消耗的更新状态。macOS / Linux 安装后由用户选择重启，Windows 安装时会关闭应用；重启前回收 Go 核心、连接和活动流。

Linux 应用内更新适用于 AppImage，deb 用户安装新 deb 包升级。0.1.3 及更早版本第一次升级需要手动安装。

## 公开资料

`screenshots/` 与 `code/refs/` 的历史图像包含内部调研环境信息，仅保留本地并被 Git 忽略。新增公开截图放到 `docs/images/`，使用隔离测试数据。连接备份、应用数据库、私钥、本地产物与依赖缓存均不应进入提交。

漏洞报告方式见 [SECURITY.md](../SECURITY.md)。维护者可在仓库设置中启用 [Private vulnerability reporting](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository)。

## 仅重试发布

如果四个平台构建已成功，但后续汇总或上传失败，可在 Actions 手动运行“构建与发布安装包”：选择 `main`，输入原版本标签，并在 `build_run_id` 填写已完成平台构建的 Run ID。该模式跳过编译，只复用原安装包。

发布前会核对构建提交与标签指向一致，并要求四个平台构建全部通过，再重新验证签名与校验值。已经公开的同名 Release 仍拒绝覆盖。发布汇总使用 Ubuntu 24.04；Linux 安装包继续在 Ubuntu 22.04 构建。
